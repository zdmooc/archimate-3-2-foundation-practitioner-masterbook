# ArchiMate — Relations, Views & Métamodèle

Glossaire des **relations**, **views/viewpoints** et concepts génériques nécessaires pour lire et construire des modèles cohérents.

**24 termes.** Chaque ligne fournit traduction, définition, exemple MayaBank, piège et renvoi.

| English | Français | Définition | Exemple MayaBank | À ne pas confondre | Voir |
|---|---|---|---|---|---|
| Composition | composition | Relation structurelle forte où la partie appartient au tout et n’a pas de sens structurel indépendant dans ce contexte. | Un Product compose plusieurs éléments constitutifs selon le modèle. | Aggregation : Composition exprime une appartenance plus forte. | [10-relations](../10-relations/README.md) |
| Aggregation | agrégation | Relation structurelle faible indiquant qu’un élément regroupe d’autres éléments. | Une architecture de domaine agrège plusieurs composants. | Composition : Aggregation autorise une autonomie plus forte des parties. | [10-relations](../10-relations/README.md) |
| Assignment | affectation | Relation indiquant qu’un élément actif exécute, porte ou est responsable d’un comportement. | Fraud Analyst assigned to Fraud Review Process. | Realization : Assignment = exécute/porte ; Realization = concrétise/implémente. | [10-relations](../10-relations/README.md) |
| Realization | réalisation | Relation indiquant qu’un élément plus concret réalise ou implémente un élément plus abstrait. | Payment Orchestrator realizes Payment Orchestration Service. | Serving : Realization relie réalisation et abstraction ; Serving relie fournisseur et consommateur. | [10-relations](../10-relations/README.md) |
| Serving | service / desserte | Relation indiquant qu’un élément fournit sa fonctionnalité à un autre élément consommateur. | Payment Orchestration Service serves Execute Instant Payment. | Realization : Serving = fournit à ; Realization = implémente. | [10-relations](../10-relations/README.md) |
| Access | accès | Relation indiquant qu’un comportement ou élément actif lit, écrit, crée ou utilise un élément passif. | Payment Validation reads Payment Transaction. | Flow : Access = interaction avec un objet passif ; Flow = transfert entre éléments. | [10-relations](../10-relations/README.md) |
| Influence | influence | Relation indiquant qu’un élément affecte positivement ou négativement un élément de Motivation. | A regulation driver influences a resilience goal. | Triggering : Influence agit sur Motivation ; Triggering exprime causalité comportementale. | [10-relations](../10-relations/README.md) |
| Association | association | Relation générique utilisée lorsqu’aucune relation sémantique plus précise n’est justifiée. | Lien documentaire entre concepts lorsqu’aucune sémantique plus forte n’est défendable. | Association-everywhere : ne pas l’utiliser pour éviter de choisir une relation correcte. | [10-relations](../10-relations/README.md) |
| Triggering | déclenchement | Relation comportementale de causalité ou de séquence. | Payment Received triggers Payment Validation. | Flow : Triggering = cause/séquence ; Flow = transfert d’information, valeur ou matière. | [10-relations](../10-relations/README.md) |
| Flow | flux | Relation indiquant un transfert entre deux éléments. | Payment Event Envelope flows from Orchestrator to Notification component. | Access : Flow représente un transfert ; Access représente lecture/écriture d’un objet passif. | [10-relations](../10-relations/README.md) |
| Specialization | spécialisation | Relation type-est-un indiquant qu’un concept est une variante plus spécifique d’un autre. | Un type spécialisé de service de paiement peut spécialiser un service plus générique. | Composition : Specialization exprime classification, pas appartenance. | [10-relations](../10-relations/README.md) |
| Junction | jonction | Élément logique permettant de combiner ou distribuer des relations du même type selon une logique AND/OR. | Une jonction peut représenter plusieurs déclenchements convergents. | Gateway BPMN : Junction est une construction ArchiMate pour relations, pas un moteur d’orchestration. | [10-relations](../10-relations/README.md) |
| Derived Relationship | relation dérivée | Relation pouvant être inférée à partir d’un chemin de relations autorisé par les règles de dérivation. | Une dépendance indirecte peut être montrée dans une vue d’impact sans dupliquer tous les liens intermédiaires. | Relation saisie arbitrairement : une relation dérivée doit suivre les règles de dérivation. | [10-relations](../10-relations/README.md) |
| Viewpoint | point de vue | Conventions déterminant comment construire une vue adaptée à certains stakeholders et concerns. | Un Technology Viewpoint guide une vue runtime pour le Platform Architect. | View : Viewpoint = comment construire ; View = représentation produite. | [11-views-viewpoints](../11-views-viewpoints/README.md) |
| View | vue | Représentation d’une sélection du modèle destinée à répondre à des concerns. | MayaBank Resilience & DR View. | Viewpoint : la vue est le résultat concret appliquant un viewpoint. | [11-views-viewpoints](../11-views-viewpoints/README.md) |
| Concern | préoccupation | Intérêt, question ou problème pertinent pour un stakeholder. | Le CISO veut comprendre le blast radius d’une perte de site. | Requirement : un concern est une question/intérêt ; une exigence est une condition à satisfaire. | [11-views-viewpoints](../11-views-viewpoints/README.md) |
| Model | modèle | Ensemble cohérent d’éléments, relations et vues décrivant une architecture. | Le modèle MayaBank contient des concepts partagés réutilisés dans plusieurs vues. | Diagram : une vue/diagramme n’est qu’une projection du modèle. | [02-metamodel](../02-metamodel/README.md) |
| Layer | couche | Regroupement de concepts selon un niveau de l’architecture, par exemple Business, Application ou Technology. | La couche Application décrit les composants et services logiciels. | Aspect : une layer répond au niveau architectural ; un aspect répond au type structure/comportement/passif. | [01-foundations](../01-foundations/README.md) |
| Aspect | aspect | Classification transversale distinguant notamment Active Structure, Behavior et Passive Structure. | Application Component = Active Structure ; Application Function = Behavior ; Data Object = Passive Structure. | Layer : l’aspect traverse les couches. | [02-metamodel](../02-metamodel/README.md) |
| Active Structure | structure active | Éléments capables d’exécuter ou de porter un comportement. | Business Actor, Application Component, Node. | Behavior : structure active = qui/quoi agit ; behavior = ce qui est fait. | [02-metamodel](../02-metamodel/README.md) |
| Behavior | comportement | Éléments décrivant une activité, fonction, processus, interaction, événement ou service. | Execute Instant Payment ou Payment Validation. | Active Structure : behavior décrit l’action, pas son porteur. | [02-metamodel](../02-metamodel/README.md) |
| Passive Structure | structure passive | Éléments sur lesquels un comportement agit. | Business Object, Data Object, Artifact, Material. | Active Structure : passif = ce qui est manipulé ; actif = ce qui agit. | [02-metamodel](../02-metamodel/README.md) |
| Internal Behavior | comportement interne | Comportement réalisé à l’intérieur d’un élément ou domaine, non nécessairement exposé. | Payment Validation est interne au Payment Orchestrator. | Service : un Service représente un comportement exposé. | [02-metamodel](../02-metamodel/README.md) |
| External Behavior | comportement externe | Comportement observable fourni à des consommateurs, généralement modélisé comme service. | Payment Orchestration Service est visible aux consommateurs. | Internal Behavior : externe = ce qui est fourni, interne = comment c’est réalisé. | [02-metamodel](../02-metamodel/README.md) |
