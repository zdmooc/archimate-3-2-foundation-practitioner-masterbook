## 22. The universal answer pattern

When you are asked an unexpected architecture question, use:

```text
1. Clarify the concern.
2. State the requirement.
3. Identify the relevant architecture level.
4. Explain the dependency or decision.
5. State the trade-off.
6. Give a recommendation.
```

Example:

**If the concern is site-level resilience, the key requirement is the RPO/RTO rather than the number of application replicas. The current design has a shared database dependency. Synchronous replication improves RPO but increases network coupling. I would compare both replication modes against measured latency and business recovery impact before selecting the target.**

## 23. Final 60-second MayaBank pitch

**MayaBank is modernizing its payment platform to support resilient real-time payments. The target separates channel APIs from payment orchestration, uses specialized services for fraud and clearing, and distributes non-critical state changes through Kafka. Workloads run on OpenShift with centralized identity, secrets and observability. The platform spans two sites, with stateful recovery driven by RPO and RTO. Migration is incremental: foundations first, hybrid flows second, target core third, and legacy decommissioning last. The main design trade-offs are consistency versus latency, centralization versus blast radius, and migration speed versus long-term architecture quality.**
